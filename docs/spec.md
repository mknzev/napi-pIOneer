# napi-pIOneer — спецификация

> Рабочее название: **napi-pIOneer** (пакет/сервис `pioneer`).
> Статус: рабочая спецификация v0.1; сверка реализации 2026-10-11 — [oneshot-audit.md](oneshot-audit.md). Знания о железе и системе — в скилле `.claude/skills/napi-c/` (прочитать перед работой).

## 1. Идея

Превратить Napi-C (RK3308, NapiLinux 0.3.x) в удобную платформу «вместо Arduino/ESP» для управления реле, кнопками, датчиками, камерами:

- **Визуальный node-редактор в стиле Blender** — граф на канвасе, рядом схема платы с подсвеченными пинами и проводами от пинов к нодам.
- **Python** как второй полноправный способ: свои блоки и скрипты.
- **Логика исполняется на плате** (браузер — только редактор и пульт), работает при закрытой вкладке и после перезагрузки.
- Удалённые устройства (ESP32-CAM и др.) — полноправные участники графа; тяжёлая обработка — на внешнем сервере по API.

Главный мокап интерфейса: [`mockups/ui-overview.webp`](mockups/ui-overview.webp) (сгенерирован; схема платы и номера пинов на нём условные — правда в `boards/napi-c.yaml`). Ранние референсы: [`mockups/flow-examples-a.webp`](mockups/flow-examples-a.webp), [`mockups/flow-examples-b.webp`](mockups/flow-examples-b.webp), стиль нод — [`mockups/blender-nodes-reference.png`](mockups/blender-nodes-reference.png).

### Цели

1. Быстро подключить железку (кнопка/реле/датчик) и накидать сценарий без кода.
2. Писать свои блоки на Python прямо в браузере, они сразу появляются в палитре.
3. Видеть живое состояние: уровни на пинах, значения на проводах, графики.
4. Несколько проектов: переключаемые и параллельные, если не делят выходы.
5. Пережить перезагрузку и OTA-обновление прошивки.

### Не-цели (пока)

- Мобильный UI (ориентируемся на ПК; пульт под телефон — потом).
- Жёсткое реальное время (WS2812, точные сервы, DHT22 bit-bang) — такое выносится на ESP/MCU, Napi им управляет.
- Двусторонняя синхронизация «граф ↔ код» (граф не генерирует Python и не парсится из него).
- Тяжёлая обработка видео на плате.
- Интеграция со штатной админкой NaPi WebUI (полностью независимый сервис).

## 2. Ограничения платформы (влияют на дизайн)

| Факт | Следствие |
|---|---|
| ~414 МБ RAM, 4×A35 | Бюджет сервиса ≤ 120 МБ RSS, idle CPU < 5 %. Никаких тяжёлых зависимостей на плате. |
| Нет пакетного менеджера и компилятора; есть Python 3.12 + fastapi 0.111, pydantic 2.8, uvicorn, sqlmodel, gpiod 2.1.3, smbus2, pyserial, psutil, dbus-fast | Бэкенд — только на этих версиях + чисто-питоновские зависимости, вендоренные в каталог приложения. |

| Логика 3.3 В, drive 2–8 мА | Только логические сигналы и модули с драйвером. UI предупреждает. |
| **Bias через gpiod игнорируется** vendor-ядром (проверено) | Runtime bias через gpiod недоступен. В админке есть план подтяжки через DT-оверлей с бэкапом и reboot; pull-up J9-7 проверен на плате после reboot. |
| ADC: 2 канала на гребёнке, 10 бит, **0…1.8 В** | Диапазон в нодах 0–1.8 В, предупреждение про делитель. |
| Аппаратный PWM на гребёнке: только PWM2 (J9-11) и PWM3 (J9-13), требует оверлей и конфликтует с I2C3 m0 (включён по умолчанию) | В фазах 0–2 — soft-PWM в отдельном потоке с `SCHED_FIFO` (≤ 500 Гц, фактический джиттер и ограничения — см. повторный замер в 11.1; для LED/реле ок, для вентилятора 25 кГц — нет). Аппаратный PWM реализован в HAL/SDK/графе; PWM2 включён и проверен на плате по sysfs; форма сигнала осциллографом не измерялась. |

| `ttyS2` занят логин-консолью | Нода UART предупреждает/предлагает отключить `serial-getty@ttyS2`. |
| Нет Wi-Fi, только Ethernet | ESP-устройства — в той же локалке через роутер. |

### Поправки к мокапам

Мокапы — общий референс по стилю. Для Napi: пины называются по гребёнке (`J9-7 · GPIO2_A4`, пользователь может дать алиас), ADC 0–1.8 В, PWM — см. выше, «вход с подтяжкой» — через DT-оверлей и reboot, «открытый сток» — эмулируется переключением направления.

## 3. Ключевые концепции

### 3.1 Описание платы (`boards/napi-c.yaml`)

Единственный источник правды о пинах для бэкенда и для SVG платы. Генерируется из [pinout скилла](../../.claude/skills/napi-c/pinout.md).

```yaml
id: napi-c
title: Napi-C
headers:
  J9: { rows: 13, cols: 2, pin1: top-left }
  J10: { rows: 13, cols: 2, pin1: top-left }
pins:
  - id: J9-7
    name: GPIO2_A4
    gpio: { chip: 2, line: 4 }  # банк gpio2; индекс /dev/gpiochipN может отличаться
    caps: [digital_in, digital_out, soft_pwm]
    alt: [I2S0_MCLK]
    default_pull: down     # из pinconf-pins
    drive_ma: 2
  - id: J9-26
    name: ADC_IN0
    caps: [analog_in]
    adc: { device: iio:device0, channel: 0, vref: 1.8 }
  - id: J9-3
    name: GPIO0_B3
    gpio: { chip: 0, line: 11 }  # банк gpio0
    caps: [digital_in, digital_out]
    interfaces: [{ name: I2C1_SDA, overlay: rk3308-i2c1 }]
  - { id: J9-1, power: 3v3 }
  # ...
```

При старте бэкенд сверяет `uEnv.txt` (`overlays=`) с `interfaces` и помечает пины, занятые включёнными интерфейсами, как `system`.

> Актуальный формат — [`napi-pioneer/boards/napi-c.yaml`](../boards/napi-c.yaml): интерфейсы вынесены в отдельный раздел `interfaces:` (группа пинов с ролями + оверлей), `caps` вычисляются кодом (см. 3.1a).

### 3.1a Режимы пина

У пина два уровня режимов с разной ценой переключения:

| Уровень | Режимы | Переключение | Кто управляет |
|---|---|---|---|
| **Функция (pinmux)** | `gpio` / `adc` или интерфейс: `uart1`, `i2c3_m0`, `spi2`, `pwm2`… | Правка `overlays=` в `uEnv.txt` + **reboot** | Только чтение в фазах 0–2; смена — фаза 3 (предпросмотр, бэкап, подтверждение) |
| **Рантайм** | `gpio_in`, `gpio_out`, `soft_pwm` (при функции `gpio`); `adc` | На лету: освободить линию → запросить заново | ResourceManager/PinIO при старте/стопе проекта, ручное управление |

- **Интерфейс — группа пинов**, включается/выключается целиком (UART1 = J9-23+J9-24). Конфликты не хранятся, а вычисляются: интерфейсы конфликтуют, если делят пин (SPI2 ⇄ UART1, UART2 m0, I2C0; PWM2 ⇄ I2C3 m0…).
- Текущая функция = включённые в `uEnv` интерфейсы (`locked`-интерфейс — консоль UART0 — включён всегда). Пин, отданный интерфейсу, в рантайм-режимах недоступен; ошибка подсказывает, что выключить и что ещё затронет («J9-11 отдан I2C3 m0 (SDA); выключите I2C3 m0 и перезагрузите»).
- `POST /board/interfaces/plan {enable, disable}` — чистый предпросмотр: новый `overlays=`, какие пины уйдут в интерфейс и какие освободятся. Конфликтующие включённые интерфейсы не выключаются молча — их надо явно перечислить в `disable`.
- Рантайм-режимы: `gpio_out`/`soft_pwm` эксклюзивны, `gpio_in`/`adc` разделяемы. Единственный владелец может сменить режим (out→in: выход сначала уходит в safe state).
- UI инспектора пина: текущая функция, доступные рантайм-режимы и «другие функции этого пина» с ценой («требует перезагрузки, затронет J9-13»).
- Фаза 3: состояние «ожидает перезагрузки» (uEnv изменён, но не применён) — сравнивать `overlays=` с тем, что прочитано при старте, и/или с `/proc/device-tree`.

### 3.2 Проект и граф

- **Проект** = `{id, name, description, autostart, graph, created/updated}`, хранится JSON-файлом `projects/<id>.json` (удобно diff/экспорт).
- **Граф** = `{nodes[], edges[], groups[]}`.
- **Нода** = `{id, type: "io.digital_out@1", position, params{}, inputs{} /*inline-значения неподключённых входов*/, collapsed, label}`.
- **Ребро** = `{from: [nodeId, socket], to: [nodeId, socket]}`.
- **Привязка к пину** — это параметр `pin` у hardware-ноды. Провод «пин платы → нода» на канвасе — визуальное отображение этого параметра (отдельный стиль), а не data-ребро. Перетаскивание с пина платы на ноду = установка `pin`.

### 3.3 Типы сокетов (цвета в духе Blender)

| Тип | Цвет | Значение |
|---|---|---|
| `Bool` | зелёный | true/false, хранит последнее значение |
| `Number` | серый | float, хранит последнее значение |
| `Event` | жёлтый | импульс «случилось», не хранит значение. Несёт данные: `{ts, payload?: Json, ctx?}` — фронт/таймер без payload, команда/сеть — с аргументами ([idea 003](ideas/003-handoff-engine.md)) |
| `String` | голубой | строка |
| `Json` | розовый | произвольный объект |
| `Image` | фиолетовый | ссылка на кадр (JPEG в буфере), не копируется по WS |
| `Request` | белый | непрозрачный контекст запроса (id, транспорт, дедлайн) — к ноде `Ответ` (фаза 2, idea 003) |

Неявные приведения: `Bool→Number` (0/1), `Number→Bool` (≠0), `Number/Bool→String`, `*→Json`. `Bool↔Event` — только явными нодами (`Edge`, `Pulse`). Несовместимые сокеты редактор не соединяет.

Неподключённый вход показывает inline-редактор значения (как `Value 0.500` в Blender). **Params** — неподключаемые настройки (дропдауны, чекбоксы).

### 3.4 Семантика исполнения

- **Реактивная push-модель.** Изменение выхода → пересчёт зависимых нод. Глобального тика нет; источники (входы, таймеры, сеть, UI) генерируют изменения.
- **Транзакции.** Изменения от одного исходного события обрабатываются одной волной в топологическом порядке (без «глитчей» — нода видит согласованные входы).
- **Волна несёт контекст** ([idea 003](ideas/003-handoff-engine.md), закладывается в фазе 1, фичи — в фазе 2):
  - `origin` — кто начал волну: `gpio:<pin>`, `timer`, `ui`, `start`, `remote:<transport>` + время. Значения на сокетах помнят источник и время последнего изменения — нужно ноде `Арбитр` (last-writer-wins) и для отладки.
  - `request?` — контекст запроса. Едет с волной неявно: посредникам (Map Range, Clamp, Арбитр) не нужно его прокидывать; `Ответ` берёт его из провода `Request`, а если провод не подключён — из волны.
  - Движок сообщает о **завершении волны** (хук) → авто-подтверждение команды без `Ответ`, таймаут ответа.
- **Внешние источники — один механизм.** `Engine.inject(source, values, ctx)` начинает новую волну; через него входят фронты GPIO, таймеры, UI-контролы и (фаза 2) команды транспортов. Отдельных путей «для сети» нет.
- **Манифест проекта.** При загрузке графа движок собирает объявления нод `Команда` / `Состояние` / событий (имена + схемы) в манифест: для discovery/HA и проверки уникальности имён среди запущенных проектов — при старте, как захват выходов (3.5).
- **Циклы** запрещены, кроме как через ноды с состоянием, разрывающие цикл (`Delay`, `Latch`, `Feedback`).
- **Состояние** у нод разрешено (`Toggle`, `Counter`, …). После перезапуска проекта состояние сбрасывается; опция «сохранять состояние» — фаза 3.
- **Ошибки** изолированы на ноде: нода краснеет, ошибка в логе, проект продолжает работать. Повторяющиеся ошибки → троттлинг.
- **Латентность**: вход → выход ≤ 20 мс (p95) для встроенных нод.
- Edge-события GPIO — через ядерный edge detection gpiod, debounce — ядерный (`debounce_period`, реально фильтрует). Запросы входов — с `event_buffer_size=1024` (дефолт 16 переполняется) и отдельным потоком-читателем.

### 3.5 Захват ресурсов и параллельные проекты

- При старте проекта рантайм **захватывает выходы** (GPIO-out, PWM, UART-TX), используемые проектом. Занято другим запущенным проектом → старт отклоняется с понятной ошибкой («J9-7 занят проектом "Полив"»).
- **Входы** GPIO-in и ADC — разделяемые. UART в текущей реализации эксклюзивен; общий UART-RX ридер ещё не реализован. Камера отложена отдельно.
- Пины `system` (интерфейсы) недоступны как GPIO.
- Ручное управление пином из UI (отладка) — только для незанятых пинов.
- **Ресурсы шире пинов** ([idea 001](ideas/001-handoff-hal.md)): `J9-7` (рантайм-режим пина), `i2c1@0x3c` (шина общая, адрес эксклюзивен), `spi2.cs0`, `uart3`, `led:user`. Шины адресуются **по id интерфейса из `boards/napi-c.yaml` без mux-варианта** — как в SDK: `I2C("i2c1", 0x3C)`, `SPI("spi2", cs=0)`, `UART("uart3", baud=115200)` ([idea 004](ideas/004-handoff-sdk.md)); `uart2` резолвится в включённый вариант (`uart2_m0`/`m1`) по живому DT, точное имя тоже принимается. Шина доступна, только если её интерфейс включён (ошибка называет оверлей и пины: «uart4 выключен: нужен оверлей `rk3308-uart4` (J10-5 TX, J10-7 RX)…»); консоль `uart0` — нельзя.
- **Занятость пинов на плате — по живому Device Tree** ([idea 002](ideas/002-vendor-docs-impact.md) п.1): узлы со `status=okay` → `pinctrl-0` → `rockchip,pins` и свойства `*-gpios`. Учитывает `user_overlays` и ядерные драйверы (`rts-gpios`, `gpio-leds`): такой пин получает функцию `kernel` («J10-17 занят драйвером ядра: serial1 (rts-gpios)»). `uEnv.txt` — «что будет после перезагрузки»; расхождение = интерфейс `pending` (↻ в UI, отдельная ошибка «включена, но ещё не применена»). Без DT (Mac/тесты) — по `uEnv.txt`.
- **Понятные ошибки занятости** (002 п.2): `EBUSY` на линии → «занят: линию держит «consumer»»; UART перед открытием проверяется по `/proc/*/fd` → «/dev/ttyS2 уже открыт: agetty (serial-getty@ttyS2.service) — остановите: systemctl stop …». Владельцы портов видны в UI (●).
- **Встроенные LED** (`user` — синий, heartbeat; `power` — зелёный, default-on): ресурс `led:<id>`, управление через `/sys/class/leds` (вкл/выкл или триггер ядра), при освобождении — системный триггер. SDK: `BoardLed("user")`.

### 3.6 Свои блоки

Два равноправных способа, оба попадают в палитру:

**a) Node Group** — выделить кусок графа → «Сгруппировать»; выбранные входы/выходы выводятся наружу. Хранится в библиотеке групп, редактируется «провалом» внутрь (Tab, как в Blender).

**b) Python-блок** — дерево файлов `blocks/<id>/block.py`, редактируется в браузере (Monaco), горячая перезагрузка:

```python
from pioneer.block import node, Node, In, Out, Param

@node(id="hysteresis", title="Гистерезис", category="Логика", color="#76528f", version=1)
class Hysteresis(Node):
    value = In("Number", default=0)
    low = In("Number", default=30)       # inline-редактируемый, можно подключить
    high = In("Number", default=35)
    invert = Param(bool, default=False)   # не подключается
    out = Out("Bool")

    def setup(self):
        self.state = False

    def on_change(self, changed: set[str]):
        if self.value >= self.high: self.state = True
        elif self.value <= self.low: self.state = False
        self.out.set(self.state != self.invert)
```

Реализовано: `on_event(name, ev)` для Event-входов, `setup`, `start`, `stop`, `on_change`, `self.log`. Пользовательские блоки выполняются в ограниченном отдельном процессе и пока не получают `self.hw`/`self.secrets`; источники с async task — план расширения, а не текущий контракт. Канонический пример — [SDK блоков](sdk/blocks.md).

**Script-нода** — SDK блоков `pioneer.block`, код живёт внутри ноды проекта. Самостоятельные скрипты с `pioneer.sdk` остаются отдельными процессами и не мигрируют автоматически.

Версионирование: `id@version`; при несовместимом изменении схемы — миграция или пометка ноды «устарела».

**Реестр типов нод (фаза 1)** собирается из нескольких источников с неймспейсами: `builtin.*` (встроенные), `user.*` (свои блоки), `mod.<module>.*` (установленные модули, [idea 001](ideas/001-modules-and-simulation.md)). Источник — часть id, конфликтов имён между источниками нет.

**Документация в схеме ноды (обязательно с фазы 1).** У каждого типа ноды (встроенной, Python-блока, группы) есть `doc`: что делает, семантика входов/выходов, пример, железные предупреждения («реле — только модулем с драйвером»). Используется палитрой/тултипами и как знание для AI-помощника (раздел 8).

### 3.7a Изменение графа только операциями (обязательно с фазы 1)

Граф меняется **не перезаписью JSON**, а списком валидируемых операций: `add_node`, `remove_node`, `set_param`, `set_input_value`, `connect`, `disconnect`, `move`, `group`, `ungroup`, `rename`. Сервер валидирует пакет операций целиком (типы сокетов, циклы, `caps` пинов, захваты) и применяет атомарно. Это даёт undo/redo, совместное редактирование вкладками — и **позволяет AI-помощнику предлагать изменения тем же языком**, что и UI.

### 3.7 Встроенные ноды (каталог v1)

- **Железо:** Digital In (кнопка: invert, debounce), Digital Out (LED/реле: invert, safe state), Analog In (канал, интервал, усреднение, диапазон 0–1.8 В), Soft PWM Out, UART Read / UART Write, Board LED. Фаза 2+: I2C Read/Write register, HW PWM.
- **Логика:** AND / OR / NOT / XOR, Compare, Hysteresis, Select (switch).
- **Математика:** Math (операция дропдауном, как в Blender), Map Range, Clamp, Expression (`{{value}} * 0.1` — безопасный вычислитель на AST, без `eval`), Smooth (скользящее среднее).
- **События и время:** Edge (Bool→Event: rising/falling/both), Pulse (Event→Bool на N мс), Toggle, Counter, Latch (SR), Debounce, Long Press, Delay, Interval, Schedule (cron), On Start.
- **UI-контролы** (источники из браузера, для тестов без железа): Button, Switch, Slider, Number. **Watch** — показывает значение/спарклайн прямо в ноде.
- **Сеть:** HTTP Request; фаза 2: HTTP Process (Image/Json → внешний сервер → ответ), Webhook In; фаза 3: MQTT In/Out.
- **Камера** (фаза 2): Camera Source, Snapshot, Save Image.
- **Отладка:** Log.

### 4.1 Плата на канвасе (ключевая фича)

- **Board-нода** — SVG-схема Napi-C, генерируется из `boards/napi-c.yaml`: две гребёнки J9/J10 2×13 в физическом расположении (метка pin 1), чтобы было удобно сверяться при подключении проводов.
- **Цвета пинов:** свободен · используется этим проектом · занят другим запущенным проектом · системный интерфейс (UART/I2C, заблокирован) · питание/GND · ADC.
- **Провода от пинов к hardware-нодам** — отдельный стиль; подсвечиваются при HIGH / по уровню ADC.
- Ховер по пину → тултип (`J9-7 · GPIO2_A4 · in/out/soft-pwm · pull-down по умолчанию · 2 мА`), клик → инспектор пина (как правая панель мокапов: режим, текущее значение, ручное управление если свободен).
- Владелец захвата в инспекторе пина (проект/скрипт) — с тултипом полного имени; **клик проваливает в этот проект/скрипт** (делается вместе со страницей скриптов).
- Board-нода может быть свёрнута в мини-вид; одна на проект, не удаляется.
- Отдельная страница **«Плата»**: та же схема со всеми проектами сразу — кто какой пин держит, live-уровни.

### 4.2 Live-режим

- Значения на проводах/сокетах обновляются по WebSocket (троттлинг до ~20 Гц на сокет).
- Индикатор у ноды: серый (стоп), зелёный (работает), красный (ошибка, текст в инспекторе).
- Изменение графа запущенного проекта → кнопка «Применить» (горячий перезапуск проекта), без автоприменения.

### 4.3 Прочие страницы

Проекты (список, автозапуск, дублирование, экспорт/импорт JSON), Мои блоки (Python-редактор + список групп), Устройства сети (ESP/камеры: адрес, статус), Секреты, Система (состояние сервиса, overlays read-only, логи).

## 5. Архитектура бэкенда

```
pioneer-core (один процесс, uvicorn 127.0.0.1:8100)
 ├─ API (FastAPI) + WebSocket
 ├─ HAL — единственный владелец железа: GPIO in/out/PWM, ADC, I2CBus, SPIDevice, UARTPort
 │    ├─ LinuxHAL: gpiod (edge-события, debounce), iio, smbus2, spidev, pyserial
 │    └─ BenchHAL — виртуальный стенд с моделями устройств (Mac, тесты, плата «всухую»)
 ├─ ResourceManager — захваты пинов и шин проектами (HW = захват + открытие в HAL)
 ├─ Engine — исполнение графов встроенных нод (asyncio)
 └─ Supervisor пользовательского кода
      └─ worker-процесс на проект (Python-блоки, Script-ноды)
           ↔ core по unix-сокету (msgpack/JSON): входы/выходы нод, вызовы HAL
```

- Пользовательский код **не исполняется в процессе core**: падение/зависание блока не роняет рантайм и не оставляет выходы в неизвестном состоянии. Таймаут на обработчик (по умолчанию 1 с) → нода в ошибку.
- Хранилище: файлы на `/mount/rfs/rw/.pioneer/data/` (`projects/`, `blocks/`, `groups/`, `secrets.json` с правами 600, `images/` — кольцевой буфер с лимитом, по умолчанию 200 МБ). SQLite не нужен на старте.
- Конфиг сервиса — `config.toml` рядом с данными.

### 5.2 Виртуальный стенд (BenchHAL)

Заложен сейчас, полноценная фича «Модули и стенд» — после фазы 1 ([idea 001](ideas/001-modules-and-simulation.md)).

- Уровень пина (сеть) = выход core (GPIO-out/PWM) → модель, которая вела пин последней → аппаратная подтяжка пина из `boards/*.yaml`.
- **Модель устройства** подключена к ресурсам: смотрит на выходы (`on_gpio`, `on_pwm` — PWM семантический: модели получают freq/duty), ведёт входы и ADC, отвечает на транзакции I2C/SPI по своему адресу/CS (нет модели → NACK `ENXIO`, как rk3x на плате), слушает/пишет UART; `state()` для UI, `action()` из UI.
- Встроенные модели: внешний уровень, перемычка, источник напряжения (= потенциометр), кнопка (с дребезгом, нажатие — против подтяжки), LED (уровень/яркость PWM), I2C-регистры (как 24C02), петли UART и SPI.
- Состав стенда — `data/bench.json`. Edge-события стенд отдаёт из своего потока, как LinuxHAL, и с той же ядерной семантикой debounce.
- `hal = "bench"` на плате — режим «всухую»: железо не трогается, uEnv/захваты — как на реальной плате.
- API: `GET /bench`, `POST /bench/models`, `DELETE /bench/models/{id}`, `POST /bench/models/{id}/actions/{name}`; WS — сообщения `bench`.

### 5.1 API (черновик)

REST под `/pioneer/api/`:

- `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`
- `GET /board` — описание платы + текущие состояния пинов + захваты
- `POST /board/pins/{id}/manual` — ручное управление свободным пином (debug)
- `GET /node-types` — схемы всех нод (встроенные + свои + группы) для палитры

- `GET|PUT|DELETE /groups/{id}`
- `GET|PUT /secrets` (значения не отдаются обратно, только ключи)
- `GET /remote-devices`, `POST /remote-devices`, `GET /camera/{id}/stream` (MJPEG-прокси), `GET /images/{id}`

## 6. Безопасность

**Железо (предупреждения в UI):** 3.3 В логика; реле — только модулем с драйвером; ADC ≤ 1.8 В (делитель); подтяжка не программная; ток пина 2–8 мА. Тексты — в карточках нод и тултипах пинов.

**Рантайм:**

- У каждого выхода есть `safe_state` (по умолчанию LOW / неактивно с учётом invert). Применяется при старте и остановке проекта, падении worker'а, остановке сервиса, `panic`.
- Нельзя назначить пин дважды, нельзя использовать `system`-пины, проверка `caps` перед стартом.
- `systemd` `Restart=on-failure` + `WatchdogSec` для core. Аппаратный `/dev/watchdog` включается явно через админку: heartbeat core, штатный disarm, по умолчанию выключен и после перезапуска сам не включается.
- Правка `uEnv.txt`/оверлеев — только фаза 3: предпросмотр diff, бэкап, проверка существования `.dtbo`, явное подтверждение, reboot отдельной кнопкой.

**Доступ:** только локалка; HTTPS через штатный nginx (`location /pioneer/` в `/etc/nginx/snippets/pioneer.conf`); вход по паролю (задаётся при `install`), сессионная cookie (HttpOnly, SameSite=Strict); CSRF-защита для мутаций. Секреты (токены внешнего сервера) — в `secrets.json`, в проекты попадают только ссылки `{{secret:name}}`.

## 9. Репозиторий и деплой

- Python-зависимости: системные пакеты платы (pin версий в `pyproject` под них) + чисто-питоновские вендоренные в `app/vendor/`. Ничего не ставить `pip install` в систему.

### 11.1 Результаты проверки на плате (2026-10-11, NapiLinux 0.3.1)

Скрипт: [`tools/probe/gpio_probe.py`](../tools/probe/gpio_probe.py), петля J9-16 (GPIO2_B2, out) ↔ J9-18 (GPIO2_B1, in).

**1. soft_reset.** `POST /system/soft_reset` → `fw_setenv resetroot yes` → `boot.scr` передаёт `rootrwreset=yes` → `/init` (из rootfs, `#!/bin/sh` = bash) выполняет `rm -rf $ROOT_RWMOUNT/*` **до** монтирования overlay. Стирается **весь корень p7**, а не только `upperdir`. Глоб `*` не захватывает dot-каталоги → `/mount/rfs/rw/.pioneer/` переживает сброс. Режим `backupbehaviour=restore` тоже делает `rm -rf $ROOT_RWMOUNT/*` и восстанавливает из бэкапа на USB. Риск: `/init` лежит в rootfs и может поменяться с OTA → `install.sh` и сервис при старте проверяют, что в `/init` по-прежнему `rm -rf $ROOT_RWMOUNT/*` (иначе — предупреждение в UI «данные могут не пережить сброс»).
Попутно: `fw_printenv` пишет «Cannot read environment, using default» — env на флеше ещё ни разу не сохранялся (CRC невалиден), U-Boot работает на встроенном дефолте; первый `fw_setenv` создаст env.

**2. gpiod edge/debounce.**
- `debounce_period` принимается и **реально работает** (в отличие от bias): 50 импульсов по 0.2 мс при debounce 10 мс → 0 событий; импульсы по 50 мс → 20/20.
- Ядерный буфер событий по умолчанию — **16 на линию**; если не вычитывать вовремя, события теряются (видно по `line_seqno`). С `event_buffer_size=1024` — 0 потерь на 1000 событий/с даже при 4 busy-loop процессах.
- Латентность фронт → userspace (Python): p50 ≈ 0.42 мс, p95 ≈ 0.5 мс (покой) / 0.7 мс (нагрузка). Бюджет 20 мс — с запасом.

**3. soft-PWM** (исторический замер до review #16; наивный цикл `sleep` до абсолютных дедлайнов, ошибка периода по ядерным таймстемпам на входе):

| Условия | 50 Гц p95 / max | 200 Гц p95 / max | 500 Гц p95 / max |
|---|---|---|---|
| покой, обычный поток | 0.18 / 1.8 мс | 0.19 / 0.9 мс | 0.12 / 15 мс |
| 4× busy-loop, обычный поток | 6.6 / 10.5 мс | 5.4 / 15 мс | 6.7 / 24 мс, теряются события |
| 4× busy-loop, `SCHED_FIFO 50` | 0.07 / 0.16 мс | 0.05 / 0.12 мс | 0.04 / 1.2 мс |

Вывод: soft-PWM — отдельный поток (или процесс) с `SCHED_FIFO`; поток-читатель edge-событий тоже RT-приоритет. Под systemd нужен `CPUSchedulingPolicy`/`LimitRTPRIO` или запуск от root (сервис и так root). Пользовательский код (worker) — обычный приоритет, чтобы не мог задушить RT-потоки.

Дополнение (проверено LinuxHAL на плате): NACK на I2C (нет устройства по адресу) драйвер rk3x отдаёт как `OSError(ENXIO=6)`, а не `EREMOTEIO`. Pillow 10.3, spidev, smbus2, pyserial — установлены; numpy — нет; glibc 2.39.

Наблюдения при пробном запуске на плате (2026-10-11): чтение живого DT ≈ 1 с (только нужные свойства); обход `/proc/*/fd` ≈ 0.3 с — один проход на все порты с кэшем 2 с. **Импорт fastapi+uvicorn на A35 ≈ 10.5 с** (с `.pyc`) — старт core ≈ 15 с; приемлемо для сервиса, ужимать (ленивые импорты / голый starlette) — при необходимости. RSS core ≈ 54 МБ, worker скрипта ≈ 14 МБ.


**Повторный замер review #25 (2026-10-11), текущий SoftPwm.** Петля J9-16 ↔ J9-18, GPIO2_B2/B1 = gpiochip4:10/9 (индексы chip после оверлеев отличаются от номера банка). Probe `pwm-production` импортирует рабочий `pioneer.hal.softpwm.SoftPwm`, PWM и читатель событий работают с SCHED_FIFO 50, буфер 1024. Перед каждым окном — 0.25 с прогрева, затем 3 с измерения; учитываются только ядерные timestamps внутри окна, без фронта безопасного закрытия. Core и его MQTT-проект продолжают работать. Нагрузка — четыре отдельных busy-loop процесса обычного приоритета.

После #16 обе фазы использовали Event.wait. При одинаковом RT-читателе p95 под нагрузкой составил 150.1 / 128.0 / 121.0 / 59.7 мкс на 50 / 100 / 200 / 500 Гц (первый прогон без прогрева). Теперь длинное ожидание остаётся прерываемым через Event.wait, финальные ≤2 мс — time.sleep до абсолютного дедлайна; close всегда ждёт поток перед safe + release. Это ограничивает задержку реакции на stop в финальном sleep двумя миллисекундами плюс задержкой планировщика, без гонки #16.

| Условия текущей реализации | 50 Гц p95 / max | 100 Гц p95 / max | 200 Гц p95 / max | 500 Гц p95 / max |
|---|---|---|---|---|
| покой, PWM + reader RT | 0.143 / 0.176 мс | 0.228 / 2.899 мс | 0.226 / 3.712 мс | 0.200 / 21.005 мс |
| 4× busy-loop, PWM + reader RT | 0.134 / 10.554 мс | 0.112 / 0.171 мс | 0.095 / 0.180 мс | 0.066 / 2.012 мс |

**Прежний ориентир p95 <0.1 мс на всех частотах не подтверждён.** Soft-PWM подходит для некритичных нагрузок, но не гарантирует жёсткий realtime или точную скважность: duty=0.5 под нагрузкой в среднем 0.48–0.50; есть редкие сильно укороченные/удлинённые фазы. Во всех окнах seq_gaps=0; в покое на 500 Гц было три последовательных события одного типа, поэтому отсутствие потерь очереди не означает, что физически наблюдался каждый фронт. Для точного сигнала нужен аппаратный PWM. Измерение проведено по GPIO IRQ timestamps, осциллограф не использовался. Исходные логи: [покой](measurements/review-25/final-rt-idle.txt), [нагрузка](measurements/review-25/final-rt-load.txt), [Event.wait до изменения](measurements/review-25/event-wait-rt-load.txt). Повторные прогоны дают разброс; таблица — один полный итоговый прогон, а не гарантированная верхняя граница.

Факты для фазы 2 (idea 003, 2026-10-11): `mosquitto` 2.0.22 установлен (сервис выключен); Python-клиента MQTT нет (`paho-mqtt` — вендорить); `websockets` 12.0 есть, `httpx` нет.
